1. `deconstruct_jointree()`: 它会把 SQL 的 jointree 拆解成 optimizer 更容易处理的结构：

- restriction clauses 分发到 base rel
- join clauses 分发到相关 join rel
- 构造 equivalence classes
- 构造 `SpecialJoinInfo`
- 生成后面 `make_one_rel()` 要用的 `joinlist`





2. `standard_qp_callback()`:在 `query_planner()` 已经完成等价类合并之后，计算本查询需要的各种排序需求，也就是填充 `PlannerInfo` 里的 `*_pathkeys` 字段，最后决定 `root->query_pathkeys`。主要工作：

- 生成 `group_pathkeys`

​       如果有 `GROUPING SETS`，使用第一个 `RollupData` 的 `groupClause` 生成分组排序需求。

​       如果是普通 `GROUP BY` 或 ordered aggregate，则用 `processed_groupClause` 生成 pathkeys，并借助等价类去掉冗余项。

​                例如 `WHERE x = y GROUP BY x, y` 中，`y` 可能被证明冗余

-  生成 `window_pathkeys`

​        如果存在窗口函数，只考虑排序逻辑中的第一个，也就是最底层的 active window，生成窗口执行需要的排序顺序生成。

- 生成`distinct_pathkeys`

​        如果有 `DISTINCT`，复制 `parse->distinctClause` 到 `root->processed_distinctClause`，再生成去重需要的排序需求；

​       如果发现不可排序，则置空。

- 生成 `sort_pathkeys`

​	直接根据 `ORDER BY` 的 `parse->sortClause` 生成最终排序需求。

- 生成 `setop_pathkeys`

​	如果当前子查询属于 set operation，并且有序结果对 setop planner 有用，则基于 setop child 的 grouplist 生成排序需求

最后根据优先级确定 `query_pathkeys`

```c
	if (root->group_pathkeys)
		root->query_pathkeys = root->group_pathkeys;
	else if (root->window_pathkeys)
		root->query_pathkeys = root->window_pathkeys;
	else if (list_length(root->distinct_pathkeys) >
			 list_length(root->sort_pathkeys))
		root->query_pathkeys = root->distinct_pathkeys;
	else if (root->sort_pathkeys)
		root->query_pathkeys = root->sort_pathkeys;
	else if (root->setop_pathkeys != NIL)
		root->query_pathkeys = root->setop_pathkeys;
	else
		root->query_pathkeys = NIL;
```

## 谓词下推

nullable_size table / nonnull_size table:可以/不可以 为空的表。eg A left join B，那么A是nonnull_size，B是null_size。

“严格”(strict)的：对于一个条件输入为null，则输出一定为null/false。eg: cno=1为严格的；cno is null则不是“strict”

1.如果是inner join ，连接条件直接下推。

 eg: select A.*,B.* from A inner join B where A.a = 1; => select A.*, B.* from (select A.* from A where A.a = 1), B where 1 = 1;

2.对于非inner join，比如left join，right join。则有**连接条件**和**过滤条件**之区别。

   2.1 连接条件下推: 如果连接条件只引用了nullable_size的表，则可以下推。引用了nonnullable_size的表则不能下推。

​         eg: select * from A left join B on A.id = 1;    **×**            (A：nonullable_size; B: nullable_size)

​         eg: select * from A left join B on B.id = 1;     **√**

  2.2 过滤条件下推: 如果过滤条件只引用了nonnullable_size，则可以下推；如果过滤条件引用了nullable_size，且过滤条件是“strict”的，则也可以下推。  (在这种情况，外连接被消除之后变成内连接)

​       eg: select * from A left join B on true where A.id = 1；      **√**       

​          select * from A left join B on true where B.id = 1;       **√**   B是nullable_size,且B.id = 1 是严格的.

​         select * from A left join B on true where A.id is null;     **√**

​         select * from A left join B on true wehre B.id is null;     **√**   B.id is null不是严格的

## 3.2 hash join 流程 

**hash join** 主要用于**两张大表等值JOIN**，非等值（><）大多数走**Nested loop join**；而**Merge join**适用于join key上都有**B-tree索引**，这样方便双指针顺序归并匹配。

**原理**：选较小表构建 Hash 表（Build 阶段），大表逐条探测（Probe）匹配哈希值。

```c
ExecHashJoin()//混合(Hybrid )hash join 算法实现，代码本质上是状态机的转移，根据node->hj_JoinState不同状态进行执行
|	|-->1. ExecHashTableCreate()// 根据计算好的nbucket，nbatch等信息分配内存，创建好node->hj_HashTable
|	|	|-->ExecChooseHashTableSize()//计算hashtable的大小（默认为 4MB）计算好nbucket（hash表插槽），nbatch(批次)
|	|-->2. MultiExecProcNode()//将内表(node->righttree)中所有tuple插入到hashtable->buckets.unshared[bucketno]中
|	|-->3. ExecHashJoinOuterGetTuple()//返回外表对应的tuple值
|	|	|-->ExecHashGetHashValue()//计算外表的此tuple的hash值(hash_key)
|	|-->4. ExecHashGetBucketAndBatch()//根据外表的haskkey去查找hashtable中对应的内表数据，如果有的话则join。并保存到内存或者临时文件中
```

**带有倾斜的混合hashjoin：**当内表的tuple很大时，通过hash函数将内表和外表进行分批次保存到磁盘中。采用批次导入，其他批次放在了临时文件里。在第一轮构建与匹配时，不仅创建了每个批次，还处理了内部表和外部表第一批次。而倾斜（skew ）批次 则在第一轮处理外表时， skew批存储了将与连接条件中涉及的属性的MCV值较大的外部表元组进行连接的内表元组（most common values）。如此外表分布越不均匀，则第一轮处理的外表元组越多。在第一轮外表探测时，如果外表中的tuple mcv值大，则跟skew批次比较。否则跟batch_0中批次比较。

主要逻辑：

- 建hashtable时会根据 outer 端统计信息里的 MCV单独建立一组skew bucket。`ExecHashBuildSkewHash()`
- `MultiExecPrivateHash()` 里对每个 inner tuple 算 hash 值后，先调 `ExecHashGetSkewBucket()`。
  如果命中 skew bucket，就进 `ExecHashSkewTableInsert()`，放到 skew 链表里。否则走普通 `ExecHashTableInsert()`。
- probe 时优先查 skew bucket。
- `ExecHashJoinNewBatch() `在刚完成 batch 0 后，会把 skewEnabled 关掉，并清空 skew 相关指针。
  所以后续 batch 不再使用 skew 优化。

   **总结**：skew 不是独立 batch，而是 batch 0 的热点值内存加速通道。它优先把高频 hash 值留在内存里，减少 spill 和后续批次 I/O；一旦超内存或第一批结束，就会被逐步收回或直接关闭。
