# 1. 背景

在 Neon 中，当计算节点（Compute）需要读取一个页面，但该页面不在本地 Buffer 时，它会向存储节点（Pageserver）发请求。

- **旧逻辑：** 计算节点通常会携带系统当前的 **`last_watched_lsn`**（即计算节点已知产生的最新日志位置）去请求页面。

- **痛点：**    Pageserver 必须保证自己已经“追”到了这个 LSN，才能把页面给计算节点。

  ​		如果 Pageserver 此时处理 WAL 日志稍微慢了一点（WAL Lag），计算节点就会卡住，进入 `LSN Wait` 状态。

  ​		事实上很多页面在过去几分钟甚至几小时内根本没变过。为了一个“老页面”去等一个“最新的 LSN”，在逻辑上是不必要的。



## 2. LwlsnCache原理

`LwLsnCache`（Lightweight LSN Cache）是一个位于计算节点内存中的哈希表，专门用来记录 **“哪个页面最后一次被修改是在哪个 LSN”**。

## 核心流程：

1. **修改时记录：** 当计算节点在底层（smgr 级别）修改一个页面并生成 WAL 时，它会顺手在 `LwLsnCache` 中记录：`Page A -> Last_Modified_LSN_100`。
2. **读取时查询：** 当计算节点需要读取 Page A 时，先查一下 `LwLsnCache`。
3. **精准请求：**
   - 如果缓存显示 Page A 最后修改于 `LSN 100`，即使系统当前最新的 `LSN` 是 `5000`，计算节点也只向 `Pageserver` 请求 `GetPage@LSN 100`。
   - **结果：** `Pageserver` 只要重放到 `LSN 100` 就能立即返回数据，而不需要等到重放完 `LSN 5000`。



# 3. 核心改动细节

## 3.1. 数据结构设计

**缓存条目（`LastWrittenLsnCacheEntry`)**

```c
typedef struct LastWrittenLsnCacheEntry
{
    BufferTag   key;           // 页面标识符（表空间、数据库、关系、fork、块号）
    XLogRecPtr  lsn;           // 该页面最后写入的 LSN
    dlist_node  lru_node;      // LRU 双向链表节点
} LastWrittenLsnCacheEntry;
```

新增的条目加入到lru中，cache满时则从头部移除最旧的条目。

**XLogCtlData 扩展**

```c
typedef struct XLogCtlData
{
    // ... 原有字段 ...
    
    /* 未缓存页面的最大 LSN */
    XLogRecPtr  maxLastWrittenLsn;
    
    /* LRU 替换策略的双向链表 */
    dlist_head lastWrittenLsnLRU;
    
    /* neon: 用于 walproposer 的 RedoStartLSN 副本 */
    XLogRecPtr  RedoStartLSN;
} XLogCtlData;
```

 **全局哈希表**：

 默认是128 * 1024 条目，由GUC 参数 **`lsn_cache_size`**设置

`static HTAB *lastWrittenLsnCache;  // 主缓存哈希表`

## 3.3 核心 API

**SetLastWrittenLSNForBlockRange() - 设置块范围的 LSN**

```c
XLogRecPtr
SetLastWrittenLSNForBlockRange(XLogRecPtr lsn, 
                              RelFileLocator rlocator,
                              ForkNumber forknum, 
                              BlockNumber from, 
                              BlockNumber n_blocks)
{
    if (lsn == InvalidXLogRecPtr || n_blocks == 0 || 
        lastWrittenLsnCacheSize == 0)
        return lsn;
    
    LWLockAcquire(LastWrittenLsnLock, LW_EXCLUSIVE);
    
    if (rlocator.relNumber == InvalidOid)
    {
        /* 更新全局最大 LSN */
        if (lsn > XLogCtl->maxLastWrittenLsn)
            XLogCtl->maxLastWrittenLsn = lsn;
        else
            lsn = XLogCtl->maxLastWrittenLsn;
    }
    else
    {
        /* 为每个块更新或插入缓存条目 */
        for (i = 0; i < n_blocks; i++)
        {
            key.blockNum = from + i;
            entry = hash_search(lastWrittenLsnCache, &key, 
                              HASH_ENTER, &found);
            
            if (found)
            {
                /* 更新现有条目 */
                if (lsn > entry->lsn)
                    entry->lsn = lsn;
                else
                    lsn = entry->lsn;
                dlist_delete(&entry->lru_node);  // 从 LRU 中移除
            }
            else
            {
                /* 新条目 */
                entry->lsn = lsn;
                
                if (hash_get_num_entries(lastWrittenLsnCache) > 
                    lastWrittenLsnCacheSize)
                {
                    /* LRU 替换：移除最旧的条目 */
                    LastWrittenLsnCacheEntry* victim = 
                        dlist_container(LastWrittenLsnCacheEntry, 
                                      lru_node,
                                      dlist_pop_head_node(&XLogCtl->lastWrittenLsnLRU));
                    
                    /* 更新全局最大 LSN */
                    if (victim->lsn > XLogCtl->maxLastWrittenLsn)
                        XLogCtl->maxLastWrittenLsn = victim->lsn;
                    
                    hash_search(lastWrittenLsnCache, victim, 
                              HASH_REMOVE, NULL);
                }
            }
            
            /* 添加到 LRU 尾部（最近使用） */
            dlist_push_tail(&XLogCtl->lastWrittenLsnLRU, &entry->lru_node);
        }
    }
    
    LWLockRelease(LastWrittenLsnLock);
    return lsn;
}
```

**GetLastWrittenLSN() - 获取页面的 LSN**

缓存命中，则使用缓存中的lsn来替代。没命中，则使用maxlsn来查找。

```c
XLogRecPtr
GetLastWrittenLSN(RelFileLocator rlocator, ForkNumber forknum, 
                  BlockNumber blkno)
{
    XLogRecPtr lsn;
    LastWrittenLsnCacheEntry* entry;
    
    LWLockAcquire(LastWrittenLsnLock, LW_SHARED);
    
    /* 默认使用全局最大 LSN */
    lsn = XLogCtl->maxLastWrittenLsn;
    
    if (rlocator.relNumber != InvalidOid)
    {
        BufferTag key = {rlocator, forknum, blkno};
        entry = hash_search(lastWrittenLsnCache, &key, HASH_FIND, NULL);
        
        if (entry != NULL)
            lsn = entry->lsn;  // 使用缓存的 LSN
        else
        {
            LWLockRelease(LastWrittenLsnLock);
            /* 缓存未命中，设置并返回 */
            return SetLastWrittenLSNForBlock(lsn, rlocator, forknum, blkno);
        }
    }
    else
    {
        /* InvalidOid：返回所有缓存条目的最大 LSN */
        HASH_SEQ_STATUS seq;
        hash_seq_init(&seq, lastWrittenLsnCache);
        while ((entry = hash_seq_search(&seq)) != NULL)
        {
            if (entry->lsn > lsn)
                lsn = entry->lsn;
        }
    }
    
    LWLockRelease(LastWrittenLsnLock);
    return lsn;
}
```



## 3.4 更新LSN缓存场景

**1. 索引构建完成后**

```c
// gininsert.c, gistbuild.c, spginsert.c
if (RelationNeedsWAL(index))
{
    log_newpage_range(index, MAIN_FORKNUM, 0, 
                     RelationGetNumberOfBlocks(index), true);
    
    /* 更新整个索引的 LSN 缓存 */
    SetLastWrittenLSNForBlockRange(XactLastRecEnd,
                                  index->rd_smgr->smgr_rlocator.locator,
                                  MAIN_FORKNUM, 0,
                                  RelationGetNumberOfBlocks(index));
    SetLastWrittenLSNForRelation(XactLastRecEnd,
                                index->rd_smgr->smgr_rlocator.locator,
                                MAIN_FORKNUM);
}
```

# 4.总结

| **维度**           | **改进前**                                       | **改进后 (LwLsnCache)**                                      |
| ------------------ | ------------------------------------------------ | ------------------------------------------------------------ |
| **查询延迟**       | 经常因为等待 Pageserver 追赶无关的 WAL 而阻塞。  | 只要目标页面已就绪，查询立即返回。                           |
| **WAL 滞后容忍度** | 容忍度低。Pageserver 稍慢，计算节点就卡住。      | **容忍度高**。只要不访问“刚刚被改动”的页面，Pageserver 慢一点也没关系。 |
| **系统稳定性**     | 写压力大时，读性能会因为日志重放积压而大幅下降。 | 读写性能进一步解耦，系统表现更平滑。                         |

PS：在后续的版本中，neon将这些改动从计算节点移动到neon中，从而进一步解耦。计算层只留下一些hook接口。
