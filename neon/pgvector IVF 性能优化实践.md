# 从页级并行到 SIMD：一次 pgvector IVF 性能优化实践

## 写在前面

向量检索的性能问题通常不是单一因素造成的。一次查询可能同时受到索引页读取、buffer 管理、距离计算、候选排序、并行调度和回表的影响。

本文记录一次针对 pgvector IVFFlat 索引的优化过程。优化从“让多个进程共同扫描索引页”开始，逐步扩展到 page directory、批量任务领取、ReadStream 读取和 SIMD 距离计算。过程中也尝试过专门的 I/O leader、显式批量读取和页顺序重排，最后根据测试结果保留有效部分，回退没有收益的路径。

这次实践的核心结论有三个：

1. 对大范围 IVF 查询，按页动态分配任务比按 list 分配任务更适合并行。
2. I/O 和计算强行拆成独立进程并没有带来收益，多个参与者自行读取和计算更有效。
3. SIMD优化确实可以改善完整查询性能，但微基准中的加速不会等比例传递到整个查询。

## 1. 原始问题：IVF查询为什么会慢

IVFFlat会先把向量划分到多个倒排分组，也就是list。查询时先选择距离查询向量最近的一些list，再扫描这些list中的索引条目，计算候选向量与查询向量之间的距离，最后返回最相近的结果。

可以把它理解成一个仓库检索过程：

1. 先决定检查哪些区域；
2. 找到这些区域对应的货架页面；
3. 读取页面中的向量；
4. 计算距离并排序；
5. 返回最相似的记录。

原始扫描流程主要由一个进程完成。即使服务器有多个CPU核心，单次查询也不能充分利用这些核心。

另一个问题是，IVF页面通常通过链表逐页发现。如果leader先把所有页面遍历一遍，才能知道后续扫描任务，那么并行扫描前已经承担了一次串行I/O成本。

当 `probes=1` 时，按list分配任务尤其不理想：查询只选择一个list，按照list分工无法产生有效并行；但这个list本身可能包含成千上万个索引页，实际上仍然可以拆分。

## 2. 第一阶段：引入页级并行扫描

第一版方案把页面作为并行任务单位，而不是把整个list作为任务单位。

leader负责完成以下准备工作：

- 获取查询向量；
- 计算查询向量与list中心的距离；
- 选择待扫描的list；
- 构建当前probe批次的数据页任务；
- 创建共享内存和排序共享状态；
- 启动worker。

leader和worker随后共同处理页面。每个参与者都执行相同的流程：

```text
领取页面任务
    → ReadBufferExtended读取索引页
    → 加共享锁
    → 遍历页内索引条目
    → 计算距离
    → 写入本地排序器
    → 释放页面
```

页面任务通过共享原子计数器领取：

```c
task = pg_atomic_fetch_add_u32(&shared->nextPage, 1);
```

这种方式有几个优点：

- 一个页面只会被一个进程处理；
- 处理快的进程可以继续领取页面；
- leader也参与实际计算，不会只负责调度；
- `probes=1`时，只要list中有多个页面，仍然可以并行；
- 不需要跨进程复制页面内容。

每个进程拥有自己的局部排序器。扫描结束后，leader等待worker完成，并将leader和worker的有序结果进行多路归并。

这里没有使用PostgreSQL执行器层面的Gather并行计划，而是在索引扫描内部创建ParallelContext。原因是IVF页面任务只有在索引扫描开始后才能构建，适合由索引访问方法自己管理。

## 3. 第二阶段：page directory减少任务准备成本

如果每次查询都沿着每个list的数据页链逐页读取，leader仍然需要先执行一次页链遍历。

因此增加了page directory。目录保存每个list实际分配的数据页块号。扫描时，leader可以直接读取目录，构建任务数组，不需要先把所有数据页链走一遍。

目录结构包含：

- 目录首页；
- 目录尾页；
- 已登记的数据页数量；
- 尾页已使用的槽位数量；
- 目录有效标志；
- 目录页之间的链指针；
- 实际数据页块号数组。

构建索引时记录真实分配的页面块号，不假设某个list一定占用连续物理页。这个约束很重要，因为索引页的连续性是当前数据布局的结果，不能当作磁盘格式保证。

### 并发INSERT如何处理

INSERT可能在已有目录之后追加新的数据页。扫描使用的是一个快照，因此目录可能落后于当前页链。

当前处理方式是：

1. 读取目录中已经登记的页面；
2. 检查最后一个登记页面的后继指针；
3. 如果存在尚未登记的尾部页面，沿页链补充；
4. 如果目录结构或追加顺序无法保证目录是完整前缀，则将目录标记为无效；
5. 之后扫描回退到完整页链。

目录失效时优先保证结果正确，不继续使用不完整的目录任务。

### VACUUM如何处理

VACUUM可以删除页面中的索引条目，但当前方案不跨list回收数据页，也不把页面重新分配给其他list。因此目录中的块号仍然有稳定含义。

这也是为什么当前没有直接引入页面generation和在线回收协议。仅保存块号时，如果允许旧页面被复用，旧扫描可能把新页面误认为旧页面，存在严重一致性风险。

## 4. 第三阶段：从逐页领取到批量领取

逐页领取的成本不只包括原子加法，还包括频繁的共享状态访问和调度竞争。

因此增加了批量领取，每个参与者默认一次领取32页任务。逻辑变成：

```c
first = pg_atomic_fetch_add_u32(&shared->nextPage, batchPages);
end = Min(first + batchPages, shared->ntasks);
```

这里的32页是任务分配粒度，不代表底层一定执行一次32页I/O。

批量领取带来的好处：

- 减少原子计数器操作次数；
- 减少任务分配的共享状态访问；
- 让参与者在本地连续处理一批任务；
- 保持动态负载均衡，处理快的参与者可以继续领取下一批。

批次也不能无限增大。批次太大时，慢进程可能提前占有过多任务，其他进程完成后只能等待；批次太小时，调度开销又会增加。

当前增加了参数：

```sql
SET ivfflat.scan_batch_pages = 32;
```

默认范围是1到128。

## 5. ReadStream和预读：为什么收益有限

PostgreSQL 17提供了ReadStream，可以根据连续块号合并读取，并提前准备后续页面。

因此增加了可选路径：每个leader或worker都复用一个自己的ReadStream。任务回调在本地批次耗尽时继续领取下一批页面。

```sql
SET ivfflat.scan_read_stream = on;
```

ReadStream路径的目标是让每个参与者拥有自己的读取前瞻能力，同时保留多个参与者自行读取页面的结构。

需要区分三个概念：

| 概念 | 含义 |
|---|---|
| 批量领取32页 | 一次从共享任务数组领取32个页任务 |
| `io_combine_limit` | buffer manager尝试合并读取的连续页上限 |
| ReadStream预读 | 提前观察后续块号并发出读取或预读建议 |

批量领取32页不等于一次底层读取32页。缓存命中、其他进程正在读取页面、页面块号不连续等情况都会改变实际读取行为。

在实际测试中，批量领取有比较稳定的小幅收益，但ReadStream的额外收益较小：

| probes | 逐页领取 | 32页批量领取 | 批量领取+ReadStream |
|---:|---:|---:|---:|
| 1 | 74.89 TPS | 76.01 TPS | 76.31 TPS |
| 100 | 1.483 TPS | 1.558 TPS | 1.583 TPS |

这些结果来自固定查询向量和单轮测试，缓存状态会影响结果。它们说明ReadStream没有带来专用I/O leader那种明显收益，也不支持单纯扩大预读窗口的结论。

## 6. 曾经尝试的专用I/O leader方案

为了让I/O和计算完全分离，曾设计过一个leader生产者：

```text
leader：读取页面并放入共享队列
worker：从队列取页面，计算距离
```

队列采用有界环形结构，页面状态大致是：

```text
FREE → READY → CLAIMED → PINNED → FREE
```

leader保留自己的页面pin，worker取得独立pin后，leader才能释放页面。

这个方案在正确性上可以成立，但性能测试暴露出供页瓶颈。worker经常等待队列中的页面，leader的读取和逐页交接速度不足以持续供给多个计算进程。

真实实例的测试结果：

| probes | 常规协作并行 | 专用I/O leader |
|---:|---:|---:|
| 1 | 52.81 TPS | 22.65 TPS |
| 100 | 1.331 TPS | 0.255 TPS |

后来增加批量发布和批量确认，供页同步开销有所下降，但仍然没有超过leader和worker各自读页、各自计算的方案。

最终回退了专用I/O leader，保留了更简单的协作式结构。

这次尝试带来的经验是：I/O和计算在模型上可以分离，但单独的I/O生产者也可能成为新的串行瓶颈。多个参与者各自进行buffer读取，通常更能利用现有的并发读取能力和负载均衡。

## 7. 页段排序：连续页面是否值得主动排序

实际检查发现，`vtest_v_idx`中的3000个list内部都是连续页区间：

| 指标 | 结果 |
|---|---:|
| list数量 | 3000 |
| 数据页总数 | 5,000,747 |
| 每个list内部是否连续 | 全部连续 |
| 至少32页的list | 1474个 |
| 位于长度至少32页区间的数据页 | 99.82% |
| 最长连续区间 | 16,681页 |

这说明当前索引布局有很好的连续读取机会。

根据这个观察，增加了可选的当前probe批次页段排序：

```sql
SET ivfflat.scan_order_pages = on;
```

实现不是根据起始页号推算后续页号，而是读取实际任务块号，识别连续段，再按连续段起始块号排序。这样不会改变任务集合，也不会依赖不可靠的连续性假设。

但排序也有成本：

- 需要额外扫描任务数组；
- 需要临时任务数组；
- 多list任务的排序会增加leader准备时间；
- 动态批量领取后，每个worker仍可能拿到不连续的任务。

隔离测试中，probes=100的结果有时变快，有时持平或略慢，没有稳定收益。因此页段排序默认关闭。

## 8. SIMD距离计算优化

前面的并行优化主要减少读取和调度成本。对每个索引条目，距离计算本身也是高频操作。

平方L2距离的核心计算是：

```c
for (int i = 0; i < dim; i++)
{
    float diff = ax[i] - bx[i];
    distance += diff * diff;
}
```

这个循环适合SIMD。AVX2每条向量指令可以处理8个float，因此增加了：

- 四路独立累加；
- AVX2非对齐加载；
- 8维块处理；
- 标量tail处理；
- 寄存器内归约；
- 128维特化路径。

128维路径完全展开，其他维度使用通用AVX2函数。64维会正常进入通用AVX2路径，执行两轮32维计算，不会越界。

### 运行时CPU分派

SIMD函数不会无条件执行。扩展初始化时检测CPU能力：

```text
CPU支持AVX2
    → 使用AVX2函数
CPU不支持AVX2
    → 使用原实现
```

通过会话参数还可以切换：

```sql
SET vector.enable_l2_simd = on;  -- 默认
SET vector.enable_l2_simd = off; -- 原自动向量化实现
```

开关通过GUC赋值回调切换函数指针，不在距离计算热循环中增加分支。

也支持事务级切换：

```sql
BEGIN;
SET LOCAL vector.enable_l2_simd = off;
-- 当前事务使用原实现
COMMIT;
```

不支持AVX2的CPU在 `on` 状态下也会自动回退。编译时可以定义 `VECTOR_DISABLE_AVX2` 强制关闭新实现。

### CPU兼容性

运行时CPU检查只保护手写AVX2函数，不能完全抵消整个扩展使用 `-march=native` 带来的跨CPU风险。

生产环境建议使用：

```bash
make clean
make PG_CONFIG=/path/to/pg_config OPTFLAGS="" -j4
```

这样基础代码使用通用指令集，只有显式标记为AVX2的函数生成AVX2代码。开发机需要本机极限性能时可以显式使用：

```bash
make PG_CONFIG=/path/to/pg_config OPTFLAGS="-march=native" -j4
```

但此类产物更适合部署到CPU能力不低于构建机的环境。

## 9. 性能结果

### 9.1 SIMD微基准

Intel Xeon Silver 4314、GCC 4.8.5、绑定单核，多轮交错测试，单位为每次距离计算纳秒：

| 维度 | 自动向量化 | 原手写AVX2 | 寄存器归约 | 128维特化 |
|---:|---:|---:|---:|---:|
| 128 | 30.50 | 25.66 | 22.83 | 18.38 |
| 768 | 165.46 | 161.37 | 158.71 | 158.87 |

128维特化相对自动向量化约1.66倍，但768维收益较小。微基准的收益不会直接等于完整查询的收益，因为完整查询还包含读页、buffer管理、锁、排序和回表。

### 9.2 实例中的c6串行IVF查询

在8999实例中删除HNSW索引后，使用唯一IVF索引，6个客户端连接，关闭索引内并行扫描：

```sql
SET ivfflat.scan_workers = 0;
SET max_parallel_workers_per_gather = 0;
```

固定768维查询向量，每组运行60秒：

| probes | 原实现TPS | AVX2 TPS | TPS提升 | 原平均延迟 | AVX2平均延迟 |
|---:|---:|---:|---:|---:|---:|
| 1 | 163.49 | **209.33** | **28.04%** | 36.68 ms | **28.64 ms** |
| 100 | 1.622 | **1.827** | **12.66%** | 3676.92 ms | **3222.06 ms** |

两组都没有失败。两个版本的Top50结果一致。

这组数据说明SIMD优化已经传递到完整IVF查询，并且在6连接串行扫描下收益高于单连接短测。原因可能包括查询计算占比更高，也可能受到缓存和执行顺序影响，因此仍应使用多轮、随机查询向量和统一缓存条件做正式容量评估。

### 9.3 大范围查询的页级并行

另一次probes=1000、单连接测试中，4个worker加leader对比串行：

| 模式 | TPS | 平均延迟 |
|---|---:|---:|
| 串行 | 0.059 | 16.91秒 |
| 4 worker + leader | 0.229 | 4.37秒 |

这说明页级并行主要解决“大量候选页需要扫描”的问题；SIMD主要优化每个候选向量的距离计算。两者作用在不同层次，可以组合使用。

## 10. 正确性与验证

本次验证覆盖：

- 串行与并行Top50比较；
- 完整候选集数量和唯一性；
- probes=1、100、1000；
- 32页批量领取；
- ReadStream开关；
- 目录开关；
- 迭代扫描；
- 重复LIMIT和运行时参数重扫描；
- 并发INSERT、DELETE和VACUUM；
- 查询取消；
- worker异常退出；
- 0个或部分worker启动；
- halfvec和bit相关回归；
- HNSW建索引与查询冒烟；
- SIMD 0～16000维和受保护内存页tail检查；
- SIMD启用、关闭、SET LOCAL、ROLLBACK和RESET；
- 14项SQL回归测试。

SIMD归约改变了浮点累加顺序，不能要求与原实现逐位一致。测试使用double参考和误差容限验证距离，查询结果集合保持一致。距离非常接近时，等距候选的顺序可能发生变化。

## 11. 产品和发布层面的结论

这次优化适合解决两类问题：

1. 单次查询需要扫描大量IVF候选页，单进程延迟过高；
2. 每个候选向量的距离计算占比较高，CPU资源充足。

并行度增加会占用更多worker和CPU资源，单连接加速比不能直接转换成高并发容量提升。实际发布时应同时观察：

- P50、P95和P99延迟；
- 总TPS；
- CPU使用率；
- worker使用量；
- shared buffer和操作系统缓存；
- 临时文件；
- 查询失败率；
- 召回率和结果稳定性。

推荐的产品描述是：

> 增强IVF向量检索的页级并行处理和L2距离计算能力，通过数据页目录、批量任务分配和CPU SIMD指令，降低大候选集查询的扫描与计算开销。实际收益取决于数据规模、查询范围、CPU型号、缓存状态和并发负载。

不建议直接表述为“所有查询提升4倍”或“并发容量提升4倍”。页级并行在重查询中可以带来较大收益，SIMD在本次c6串行测试中带来约13%～28%的吞吐提升，但这些结果仍需要结合业务数据和多轮压力测试确认。

## 12. 后续方向

后续可以继续做的工作包括：

- 在真实业务数据上进行多轮随机向量测试；
- 按CPU型号分别建立基准；
- 增加底层实际读取大小、CPU周期和I/O等待统计；
- 测试AVX2、AVX-512和FMA路径；
- 设计批量距离接口，减少函数调用和查询向量重复加载；
- 评估数据库高并发下的worker资源竞争；
- 继续研究HNSW已发现邻居的批量预读，而不是直接套用IVF页任务模型。

当前已经确认的稳定方向是：page directory、页级动态并行、32页批量领取和可控的SIMD距离计算。专用I/O leader、激进预读和页段排序仍应保持实验属性，依据实际业务数据决定是否启用。
