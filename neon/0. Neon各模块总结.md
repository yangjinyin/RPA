# Neon 模块学习总览

本文面向研发和产品同学，介绍 Neon 的主要模块、职责边界以及一条 SQL 从执行到持久化、再到页面读取的完整链路。

## 一、整体架构

Neon 将 PostgreSQL 的计算和持久化存储拆开：

```text
客户端
  ↓
Proxy
  ↓
Compute（PostgreSQL）
  ↓ 生成 WAL
walproposer
  ↓ 复制 WAL
Safekeeper 集群
  ↓ 提供 WAL
Pageserver
  ↓ 保存页面历史
Remote Storage
```

各模块关注的问题不同：

| 模块 | 主要职责 |
| --- | --- |
| Compute | 执行 SQL、事务和产生 WAL |
| walproposer | 将 WAL 复制到 Safekeeper，并完成多数派确认 |
| Safekeeper | 持久化连续 WAL，参与共识并向 Pageserver 提供 WAL |
| WAL decoder | 将 PostgreSQL 原始 WAL 解析成结构化记录 |
| Pageserver | 保存按 LSN 版本化的页面和元数据 |
| Layer | 保存某个 Key 在不同 LSN 下的页面版本或 WAL 记录 |
| WAL redo | 根据基础页面和 WAL 记录重建目标页面 |
| Timeline | 管理一条数据库历史分支 |
| Compaction/GC | 合并 Layer、回收不再需要的历史版本 |
| Remote Storage | 持久化 Layer、索引和 Timeline 元数据 |
| Proxy | 将客户端连接路由到 Compute |
| Control Plane | 管理租户、Compute、Pageserver 和 Safekeeper 等资源 |

## 二、核心数据链路

### 1. 写入链路

客户端执行 `INSERT`、`UPDATE`、`DELETE` 或 `COMMIT` 时，Compute 中的 PostgreSQL 会修改内存页面并生成 WAL：

```text
SQL
  ↓
PostgreSQL backend 修改 buffer
  ↓
生成 WAL record
  ↓
walproposer 读取 WAL
  ↓
发送给多个 Safekeeper
  ↓
多数 Safekeeper flush
  ↓
推进 commit_lsn
```

`commit_lsn` 表示已经被 Safekeeper 多数派确认的 WAL 位置。它和单个节点的 `flush_lsn` 不同：

```text
flush_lsn = 某一个 Safekeeper 已经刷盘的 WAL 位置
commit_lsn = 多数 Safekeeper 已经确认的 WAL 位置
```

### 2. Pageserver ingest 链路

Pageserver 从 Safekeeper 获取 WAL 后，不会把整个 PostgreSQL 数据目录直接复制过来，而是把 WAL 转换成页面历史：

```text
Safekeeper
  ↓ XLogData
WAL receiver
  ↓
WAL decoder
  ↓
InterpretedWalRecord
  ↓
WalIngest::ingest_record()
  ↓
DatadirModification
  ↓
InMemoryLayer
  ↓
DeltaLayer / ImageLayer
```

源码入口：

```text
pageserver/src/walingest.rs
pageserver/src/pgdatadir_mapping.rs
libs/wal_decoder/
```

### 3. 页面读取链路

Compute 请求某个关系文件的某个 block 时，会同时带上 Tenant、Timeline、Key 和 LSN：

```text
Compute 请求页面（Key, LSN）
  ↓
Pageserver 定位 Timeline
  ↓
从 Layer 找到基础 image 和后续 WAL record
  ↓
按 LSN 顺序执行 WAL redo
  ↓
返回目标 LSN 的页面
```

因此，Pageserver 提供的不是一个固定的最新页面，而是：

```text
某个页面在指定 LSN 时刻的内容
```

## 三、各个核心模块

## 3.1 Compute

Compute 是运行 PostgreSQL 的计算节点，负责实际执行数据库工作：

- 解析和执行 SQL；
- 管理连接、事务和锁；
- 管理 PostgreSQL buffer cache；
- 修改 heap、index、系统目录和 SLRU；
- 生成 WAL；
- 执行本地查询和事务可见性判断。

Compute 的数据页是临时缓存，持久化结果主要由 WAL 和 Pageserver 页面历史保证。

相关目录：

```text
compute/
compute_tools/
pgxn/neon/
```

## 3.2 walproposer

`walproposer` 是运行在 Compute 内部的 PostgreSQL 后台进程，负责将 Compute 产生的 WAL 复制到 Safekeeper。

它在协议中扮演 proposer 角色，Safekeeper 扮演 acceptor 角色：

```text
walproposer = proposer
safekeeper  = acceptor
```

主要职责：

- 读取 PostgreSQL 产生的 WAL；
- 连接多个 Safekeeper；
- 发起 proposer 选举；
- 维护 term；
- 发送 `AppendRequest`；
- 等待多数 Safekeeper 持久化；
- 推进 `commit_lsn`；
- 处理 Safekeeper 掉线、重连和 WAL 恢复。

源码：

```text
pgxn/neon/walproposer.c
pgxn/neon/walproposer_pg.c
pgxn/neon/walproposer.h
```

## 3.3 Safekeeper

Safekeeper 是 WAL 的可靠存储和复制节点。它保存连续 WAL，但不负责把 WAL 转换成最终的关系页面。

主要职责：

- 接收 walproposer 发来的 WAL；
- 校验 term、起始 LSN 和 WAL 连续性；
- 将 WAL 写入本地 WAL storage；
- flush WAL 到磁盘；
- 参与 proposer/acceptor 共识；
- 维护 `flush_lsn` 和 `commit_lsn`；
- 从其他 Safekeeper 补齐缺失 WAL；
- 响应 Pageserver 的复制请求；
- 支持 Compute 故障后的 WAL 恢复。

主要源码：

```text
safekeeper/src/receive_wal.rs
safekeeper/src/safekeeper.rs
safekeeper/src/send_wal.rs
safekeeper/src/wal_service.rs
safekeeper/src/timeline.rs
safekeeper/src/recovery.rs
```

### Safekeeper 的两个方向

Compute 到 Safekeeper：

```text
walproposer → receive_wal → Safekeeper WAL storage
```

Safekeeper 到 Pageserver：

```text
Pageserver 发起拉取请求
  ↓
Safekeeper send_wal
  ↓
XLogData
```

Safekeeper 的 `send_wal.rs` 发送的是原始 WAL 字节。事务、heap、CLOG 等 record 的具体解析由 Pageserver 的 WAL decoder 完成。

## 3.4 WAL decoder

WAL decoder 负责将 PostgreSQL 原始 WAL 字节解析成结构化数据：

```text
原始 WAL
  ↓
解析 resource manager
  ↓
识别 record 类型
  ↓
提取 relation、block、XID、LSN 等信息
  ↓
构造 InterpretedWalRecord
```

它可以识别：

- heap 和 index 页面记录；
- INSERT、UPDATE、DELETE；
- COMMIT、ABORT、PREPARE；
- CLOG 和 MultiXact；
- Visibility Map；
- relation create/drop/truncate；
- relmap；
- logical message；
- replication origin。

相关目录：

```text
libs/wal_decoder/
```

## 3.5 Pageserver

Pageserver 是 Neon 的页面存储服务，负责维护页面的 LSN 历史。

主要职责：

- 从 Safekeeper 拉取 WAL；
- 解码 PostgreSQL WAL record；
- 将 record 映射到 Pageserver 的 Key；
- 保存 page image 和 WAL record；
- 按指定 LSN 提供页面；
- 执行 WAL redo；
- 管理 Layer；
- 执行 compaction 和 GC；
- 从 Remote Storage 加载缺失数据。

主要源码：

```text
pageserver/src/walingest.rs
pageserver/src/pgdatadir_mapping.rs
pageserver/src/walredo.rs
pageserver/src/page_service.rs
pageserver/src/tenant/
```

## 3.6 Layer

Layer 是 Pageserver 的版本化存储单元，可以理解为：

```text
Key 范围 + LSN 范围 + 页面版本或 WAL record
```

常见类型：

```text
InMemoryLayer
    正在接收 WAL 的内存层

DeltaLayer
    保存页面变化和 WAL record

ImageLayer
    保存某个 LSN 范围内的完整页面 image
```

Layer 中保存的 Key 不只包括普通表页面，还包括：

- heap/index/FSM/VM 页面；
- CLOG 页面；
- MultiXact 页面；
- relmap；
- relation size；
- 数据库目录；
- 两阶段事务文件；
- 其他 PostgreSQL 元数据。

同一个页面可以有多个历史版本：

```text
Key=A, LSN=100：旧页面
Key=A, LSN=150：UPDATE 后页面
Key=A, LSN=200：VACUUM 后页面
```

## 3.7 WAL redo

WAL redo 根据基础页面和 WAL record 重建目标页面：

```text
基础 page image
  ↓
应用后续 WAL record
  ↓
得到目标 LSN 的页面
```

Pageserver 使用两类 redo：

- Neon 内部 redo：处理 CLOG、MultiXact、部分 Visibility Map 等特殊记录；
- PostgreSQL redo：处理复杂的 PostgreSQL WAL record。

相关源码：

```text
pageserver/src/walredo.rs
pageserver/src/walredo/apply_neon.rs
```

## 3.8 事务、CLOG 和 Layer

PostgreSQL heap tuple 中的 `xmin`、`xmax` 不能单独决定 tuple 是否可见，还需要查询 CLOG 中的事务状态。

例如：

```text
LSN 100：xid=42 插入 tuple
LSN 120：xid=42 COMMIT
```

查询 LSN 110 时，tuple 不应可见；查询 LSN 130 时，tuple 应该可见。

因此 Pageserver 必须把事务状态也纳入 LSN 历史。`XactRecord` 会被转换为类似下面的特殊记录：

```rust
NeonWalRecord::ClogSetCommitted { .. }
NeonWalRecord::ClogSetAborted { .. }
```

这不是 Layer 在执行完整事务，而是 Pageserver 将影响页面可见性的事务元数据保存成可按 LSN 查询的版本。

## 3.9 VACUUM

VACUUM 仍然由 Compute 中的 PostgreSQL 执行，Pageserver 只接收 VACUUM 产生的 WAL。

VACUUM 可能修改：

- heap 页面；
- Visibility Map；
- tuple 的冻结状态；
- CLOG 相关状态；
- relation size；
- 页面中的空闲空间。

处理流程：

```text
PostgreSQL 执行 VACUUM
  ↓
生成 heap/VM 等 WAL
  ↓
Safekeeper 持久化 WAL
  ↓
Pageserver 解码并写入新的页面版本
  ↓
后续读取时按目标 LSN 重放
```

VACUUM 生成新版本后，旧版本不会立即删除，因为旧版本可能仍被分支或 PITR 查询使用。旧版本由 GC compaction 在确认不再需要后回收。

## 3.10 Timeline

Timeline 表示一条数据库历史分支，包含：

- Tenant；
- Timeline ID；
- 父 Timeline；
- 分叉 LSN；
- 当前 WAL 位置；
- Layer 集合。

例如：

```text
主 Timeline：LSN 0 → 100 → 200 → 300
子 Timeline：从 LSN 200 分叉，继承 0 → 200
```

Timeline 支持：

- 创建数据库分支；
- 时间点恢复；
- 多个分支共享祖先历史；
- 每个分支独立接收后续 WAL。

## 3.11 TenantManager 和 Tenant

Pageserver 使用以下层级管理数据：

```text
Pageserver
  └── TenantManager
        └── Tenant
              └── Timeline
                    └── Layer
```

`TenantManager` 负责：

- 加载和卸载 Tenant；
- 创建和删除 Timeline；
- 管理 Tenant 生命周期；
- 调度后台任务；
- 管理远程存储和本地缓存。

## 3.12 Page Service

Page Service 是 Pageserver 面向 Compute 的页面读取接口。

一次页面请求通常包含：

```text
Tenant
Timeline
Relation
Block
LSN
```

处理步骤：

```text
定位 Timeline
  ↓
根据 Key + LSN 查找 Layer
  ↓
读取 image 或 WAL record
  ↓
执行 redo
  ↓
返回页面
```

## 3.13 Compaction 和 GC

### Compaction

Compaction 合并多个 Layer，减少读取时需要遍历的 Layer 数量：

```text
多个 DeltaLayer
  ↓
合并
  ↓
更少的 DeltaLayer 或 ImageLayer
```

它改变数据的物理组织方式，不改变数据库逻辑结果。

### GC compaction

GC compaction 回收不再需要的历史版本。判断时需要考虑：

- 当前 Timeline 的保留点；
- 子 Timeline 的分叉点；
- PITR 保留策略；
- 正在进行的读取；
- Remote Storage 状态。

因此：

```text
VACUUM = 生成新的数据库页面状态
GC      = 回收已经无人使用的旧页面历史
```

## 3.14 Remote Storage

Remote Storage 通常是 S3 或兼容对象存储，用于保存：

- Layer 文件；
- Timeline metadata；
- Layer index；
- WAL 备份或相关持久化数据。

Pageserver 本地缓存缺失时，可以从 Remote Storage 下载 Layer。

## 3.15 Proxy 和 Control Plane

Proxy 位于客户端和 Compute 之间，负责：

- 接收客户端连接；
- 根据租户和数据库信息选择 Compute；
- 转发连接；
- 配合 Compute 的启动、休眠和切换。

Control Plane 负责控制面资源管理：

- 创建 Tenant；
- 创建 Timeline；
- 分配 Compute；
- 分配 Pageserver 和 Safekeeper；
- 维护服务配置和节点关系；
- 管理服务生命周期。

## 四、关键概念对照

| 概念 | 含义 |
| --- | --- |
| WAL | 描述数据库变化的日志 |
| LSN | WAL 中的位置，用于标识数据库历史进度 |
| `flush_lsn` | 某个 Safekeeper 已刷盘的 WAL 位置 |
| `commit_lsn` | Safekeeper 多数派确认的 WAL 位置 |
| Key | Pageserver 中定位页面或元数据的逻辑键 |
| Layer | 按 Key 和 LSN 保存数据历史的存储单元 |
| Timeline | 一条数据库历史分支 |
| DeltaLayer | 保存页面变化或 WAL record |
| ImageLayer | 保存完整页面 image |
| WAL redo | 根据 WAL 重建目标页面 |
| CLOG | 保存事务提交、回滚等状态 |
| Visibility Map | 记录 heap 页面可见性和冻结状态 |
| Compaction | 合并 Layer，减少读取开销 |
| GC | 回收不再需要的历史版本 |

## 六、最重要的一条主线

阅读代码时，可以始终围绕下面的问题展开：

```text
一次 SQL 修改了什么？
  ↓
PostgreSQL 生成了哪些 WAL？
  ↓
walproposer 如何复制这些 WAL？
  ↓
Safekeeper 如何保证 WAL 连续并持久化？
  ↓
Pageserver 如何解析 WAL？
  ↓
这些变化写入了哪个 Key 和哪个 Layer？
  ↓
Compute 按某个 LSN 读取页面时如何重建？
```

用一句话概括各模块：

> Compute 产生数据库变化，walproposer 复制 WAL，Safekeeper 可靠保存 WAL，Pageserver 将 WAL 转成按 LSN 管理的页面历史，Layer 保存这些历史，Timeline 组织数据库分支，WAL redo 重建页面，Compaction 和 GC 负责优化和回收。
