

# 1.启动时崩溃恢复逻辑改动

## 背景知识

pg需要恢复的条件是：

- pg_control中的数据库状态不正常（非`DB_SHUTDOWNED`）
- pg_control中记录的最新检查点读取不到`XLOG`日志文件

#### **关键差异**

1. **无WAL启动**: Neon可能在完全没有读取WAL的情况下启动
2. **页面初始化**: 需要从头构建WAL页面头部
3. 在第三阶段(`FinishWalRecovery()`) neon做了写特殊处理

```c
	result->standby_signal_file_found = standby_signal_file_found;
	result->recovery_signal_file_found = recovery_signal_file_found;

	return result;
}
```

# 2. FPI(full page image) 核心改动

在标准的 PostgreSQL 中，全页图像（FPI）是为了防止因对本地存储进行非原子性 8 KB 页面写入而导致的撕裂页面写入问题。

而在Neon架构中，通常不需要 FPI，因为计算节点从不就地覆盖页面。相反，所有的修改都作为 WAL 记录记录下来，并发送到页面服务器。

#### 核心钩子机制

```c
/* NEON: Hook to determine if FPI should be suppressed for a WAL record */
typedef bool (*xlog_should_suppress_fpi_hook_type)(void);
extern PGDLLIMPORT xlog_should_suppress_fpi_hook_type xlog_should_suppress_fpi_hook;

/* NEON: Global flag to suppress FPI for current WAL record */
bool suppress_fpi = false;
```

#### WAL插入时的FPI检查逻辑
在 `XLogInsert()` 函数中添加的关键代码：
```c
/*
 * NEON: Check if we should suppress FPI for this WAL record.
 */
suppress_fpi = false;
if (xlog_should_suppress_fpi_hook != NULL) {
    suppress_fpi = xlog_should_suppress_fpi_hook();
    elog(DEBUG1, "FPI suppress hook called: suppress_fpi=%d, doPageWrites=%d",
         suppress_fpi, doPageWrites);
}
```

#### 重新计算逻辑的调整
在 `XLogInsertRecord()` 中 会跳过涉及到fpi的WAL record
```c
/*
 * However, if suppress_fpi is true, we skip the recomputation check
 * since we're deliberately suppressing full page images for this
 * record via the FPI control hook.
 */
if (doPageWrites &&
    (!prevDoPageWrites ||
     (!suppress_fpi &&
      fpw_lsn != InvalidXLogRecPtr && fpw_lsn <= RedoRecPtr)))
```



# 3.WAL的改动

## 背景知识

在 PostgreSQL 的 MVCC 机制中，判断一个元组（Tuple）是否可见，需要两个关键的事务标识：

- **XID (Transaction ID)：** 哪个事务产生的修改。
- **CID (Command ID)：** 在同一个事务内部，是第几个命令产生的修改。

**原生 Postgres 的逻辑：** 在标准磁盘存储中，`cid` 存储在元组头（Tuple Header）中。但在生成 WAL 日志时，由于性能考虑，原生 Postgres 的 `INSERT/UPDATE/DELETE` 日志并不总是显式包含 `cid`。它假设在恢复（Recovery）时，从`clog`中可以获取事务的状态信息。

**Neon 的架构中**： 如果 WAL 记录中缺失 `cid`，Pageserver 在将日志应用到数据页上时，无法正确设置元组头部的 `cmin/cmax`（即 `cid`）。如果涉及同一个事务内的多次操作（例如：一个事务内先 INSERT 再 SELECT），可能会因为 `cid` 错误导致快照可见性判定失效，看到不该看到的数据或看不到该看到的数据。



### update举例

```c
typedef struct xl_heap_update
{
	TransactionId old_xmax;		/* 记录update旧元组的xmax */
	OffsetNumber old_offnum;	/* 记录旧元组在其page中的相对位置 */
	uint8		old_infobits_set;	/* 记录旧元组的t_infomask和t_infomask2的值 */
	uint8		flags;
	TransactionId new_xmax;		/* 记录新元组的xmax */
	OffsetNumber new_offnum;	/* 记录新元组在其page中的相对位置 */

	 * If XLH_UPDATE_CONTAINS_OLD_TUPLE or XLH_UPDATE_CONTAINS_OLD_KEY flags
	 * are set, xl_heap_header and tuple data for the old tuple follow.
	 */
} xl_heap_update;
```

## Neon核心改动

为了解决上述问题，该提交将原生的 DML（INSERT/UPDATE/DELETE）日志记录替换成了 Neon 特有的自定义版本（详细在neon_xlog.h）

#### A. 记录结构的改变

Neon 引入了新的 WAL  类型。

- **原生:** `xl_heap_insert` 等结构体不包含 `cid`。

- **Neon Custom:** 在 `xl_heap_insert`、`xl_heap_update` 和 `xl_heap_delete` 的记录头部新增`cid`

  ```c
  typedef struct xl_neon_heap_update
  {
  	TransactionId old_xmax;		/* xmax of the old tuple */
  	OffsetNumber old_offnum;	/* old tuple's offset */
  	uint8		old_infobits_set;	/* infomask bits to set on old tuple */
  	uint8		flags;
  	uint32		t_cid;			//新增
  	TransactionId new_xmax;		/* xmax of the new tuple */
  	OffsetNumber new_offnum;	/* new tuple's offset */
  
  	/*
  	 * If XLH_UPDATE_CONTAINS_OLD_TUPLE or XLH_UPDATE_CONTAINS_OLD_KEY flags
  	 * are set, xl_neon_heap_header and tuple data for the old tuple follow.
  	 */
  } xl_neon_heap_update;
  ```

  

#### B. `heapam.c` 的拦截

在元组操作（Heap Access Methods）层，Neon 修改了 `log_heap_update` 等函数：

1. **捕获当前事务的 `cid`：** 通过 `GetCurrentCommandId(true)` 获取。
2. **使用新type插入wal：** 放弃调用原生的 `XLogRegisterData` 逻辑，转而使用包含 `cid` 的 Neon 结构体进行打包。

#### C. Pageserver 端的适配

Pageserver 的 Redo 逻辑同步更新，以识别这些自定义记录。

- 当 Pageserver 看到这些记录时，它能精确地提取出 `cid` 并写入目标 Page 的元组槽位中。
- 这确保了存储在远端（S3）的数据页在物理上是“MVCC 完备”的。



核心回放函数**`redo_neon_heap_update()`**,通常涉及两个动作：

1. **修改旧元组（Old Tuple）**：设置 `XMAX`（标记删除）并指向新版本。
2. **插入新元组（New Tuple）**：写入新数据并设置 `XMIN`
