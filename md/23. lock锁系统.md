# 一.Lock management

## lock_sys_t

 是innodb锁系统的重要全局结构，管理所有锁系统。

在lock0lock.h中声明了全局的锁系统：**extern lock_sys_t *lock_sys**

![lock_entrance](http://catkang.github.io/assets/img/innodb_lock/lock_entrance.png)

 **主要作用：**

1. 维护当前全局的事务加锁和锁等待的信息
2. 在有新的加锁需求的时候，需要判断跟当前已有事务锁是否冲突，如果冲突需要将新的加锁需求挂起。
3. 当有事务锁被释放掉的时候，挂起等待在这个锁上的请求应该被唤醒并重新完成加锁，继续后续的操作。
4. 为了避免过长的锁等待，还需要有锁超时，以及死锁检测及处理机制。



```c++
struct lock_sys_t {
  //保护 rec locks和table locks的闩锁集合
  locksys::Latches latches;

  /** 普通的 Next-Key Lock、Gap Lock、Record Lock
      实现: 使用页号作为哈希键，存储该页面上的所有行锁*/
  hash_table_t *rec_hash;

  /** 谓词锁的哈希表
     用途: 用于空间索引（GIS）的谓词锁，支持多维空间查询 */
  hash_table_t *prdt_hash;

  /**谓词页锁的哈希表 用途: 页级别的空间索引锁*/
  hash_table_t *prdt_page_hash;

  /** Padding to avoid false sharing of wait_mutex field */
  char pad2[ut::INNODB_CACHE_LINE_SIZE];

  /** 保护: waiting_threads 和 last_slot的互斥锁 */
  Lock_mutex wait_mutex;

  /**  等待锁的用户线程数组. */
  srv_slot_t *waiting_threads;

  /** waiting_threads 数组中曾经使用过的最高槽位. */
  srv_slot_t *last_slot;

  /** 标识是否所有恢复事务的回滚已完成。用途: 数据库启动时的恢复流程 */
  bool rollback_complete;

  /** 作用: 观察到的最大锁等待时间 */
  std::chrono::steady_clock::duration n_lock_max_wait_time;

  /**  锁等待超时监控线程创建的事件 */
  os_event_t timeout_event;
};
```



## lock_t

是 InnoDB 锁系统中表示单个锁的核心数据结构。

```c++
struct lock_t {
  /** 指向拥有此锁的事务*/
  trx_t *trx;

  /** 事务锁列表节点，将该锁链接到事务的锁列表中，一个事务可以持有多个锁 */
  UT_LIST_NODE_T(lock_t) trx_locks;

  /** 仅对记录锁有效，标识锁定的是哪个索引上的记录 */
  dict_index_t *index;

  /** 用于在哈希表中通过单链表连接相同哈希值的锁. */
  lock_t *hash;

  union {
    /** Table lock 表锁 */
    lock_table_t tab_lock;

    /** Record lock 记录锁*/
    lock_rec_t rec_lock;
    
    /** 锁类型和模式的位标志组合;
        锁模式：LOCK_S (共享锁) 或 LOCK_X (排他锁)
        锁类型：LOCK_TABLE (表锁) 或 LOCK_REC (记录锁)
        锁修饰符：
				LOCK_GAP (间隙锁)
				LOCK_REC_NOT_GAP (仅锁记录，不锁间隙)
				LOCK_INSERT_INTENTION (插入意向锁)
				LOCK_WAIT (等待标志)
				LOCK_PREDICATE (谓词锁)
				LOCK_PRDT_PAGE (谓词页锁)		*/
    uint32_t type_mode;
  };

```

## 2.1 对记录加锁

核心函数 `lock_rec_lock()`，分为fast 和slow 两种方式。

Fast方式：不需要做冲突检测的。比如：page上没有锁；或者当前page只有一个锁，且锁类型跟本次需求一致。创建成功后锁要加入到		 **lock hash** 以及 **trx_locks**中（见上图）

Slow方式：做会冲突检测；以前也会做死锁检测，现在版本不再做了。

### rec_lock_check_conflict() 锁冲突检测

**规则1：同一事务或锁模式兼容**

同一事务的锁不冲突（事务可以多次锁定同一记录）

```c++
if (trx == lock2->trx ||
    lock_mode_compatible(static_cast<lock_mode>(LOCK_MODE_MASK & type_mode),
                         lock_get_mode(lock2))) {
    return Conflict::NO_CONFLICT;
}
```

锁冲突矩阵

```c++
static const byte lock_compatibility_matrix[5][5] = {
    /**         IS     IX       S     X       AI */
    /* IS */ {true, true, true, false, true},
    /* IX */ {true, true, false, false, true},
    /* S  */ {true, false, true, false, false},
    /* X  */ {false, false, false, false, false},
    /* AI */ {true, true, false, false, false}};
```



**规则2：高优先级事务可以忽略非高优先级的等待锁**

eg：

锁队列:   [T1(已授予 X)] → [T2(等待 X)] → [HP-T3(请求 X)]
结果:      HP-T3 可以绕过 T2 的等待锁

```c++
const bool is_hp = trx_is_high_priority(trx);
if (is_hp && lock2->is_waiting() && !trx_is_high_priority(lock2->trx)) {
    return Conflict::NO_CONFLICT;
}
```



**规则3：GAP 锁（非插入意向）不需要等待** 

GAP锁之间**不冲突**；原因在于gap锁只是防止插入，不锁定现有记录

```c++
if ((lock_is_on_supremum || (type_mode & LOCK_GAP)) &&
    !(type_mode & LOCK_INSERT_INTENTION)) {
    /* Gap type locks without LOCK_INSERT_INTENTION flag
    do not need to wait for anything. */
    return Conflict::NO_CONFLICT;
}
```



**规则4: Record Lock 不需要等待 GAP 锁**

```c++
if (!(type_mode & LOCK_INSERT_INTENTION) && lock_rec_get_gap(lock2)) {
    /* Record lock (LOCK_ORDINARY or LOCK_REC_NOT_GAP)
    does not need to wait for a gap type lock */
    return Conflict::NO_CONFLICT;
}
```



**规则5: GAP 锁不需要等待 REC_NOT_GAP 锁**

```c++
if ((type_mode & LOCK_GAP) && lock_rec_get_rec_not_gap(lock2)) {
    /* Lock on gap does not need to wait for
    a LOCK_REC_NOT_GAP type lock */
    return Conflict::NO_CONFLICT;
}
```



**规则6: 插入意向锁不会阻塞其他锁**

```c++
if (lock_rec_get_insert_intention(lock2)) {
    /* No lock request needs to wait for an insert
    intention lock to be removed. */
    return Conflict::NO_CONFLICT;
}
```



**规则7: ByPass规则**

- T2 在等待 T1 释放锁
- T3 也在等待 T1
- T3 绕过 T2 不会改变 T2 的等待状态
- 优化：允许 T3 也等待 T1，而不是串行等待。并返回CAN_BYPASS

```c++
if (!(type_mode & LOCK_INSERT_INTENTION) && lock2->is_waiting() &&
    lock2->mode() == LOCK_X && (type_mode & LOCK_MODE_MASK) == LOCK_X) {
    
    /* 如果请求事务已经持有一个GRANTED锁阻塞了lock2，
       则可以绕过lock2 */
    if (trx_locks_cache.has_granted_blocker(trx, lock2)) {
        return Conflict::CAN_BYPASS;
    }
}
```



**规则8：必须等待**

return Conflict::HAS_TO_WAIT;

## 计算调度权重

在获取了所有的等待事务关系图后，需要根据其阻塞的事务数量开始计算权重（ `lock_wait_compute_and_publish_weights_except_cycles()`）, 过程如下：

- `lock_wait_compute_initial_weights()`: 初始化权重, 初始值为 1. InnoDB 新增了一个全局自增变量 lock_wait_table_reservations, 在每个线程因为锁等待进入等待状态时, 会获取当时的 lock_wait_table_reservations 的值, 所以每个事务自身的 table_reservations 与全局的 lock_wait_table_reservations 的差值代表了等待的时间, 差值越大等待时间越长. 所以在事务锁的调度算法中, 为了防止有事务饿死的情况, 将差值超过等待事务数量的事务权重设为等待事务数量。
- `lock_wait_compute_incoming_count():` 更新事务等待关系图中的入度情况, 即一个事务阻塞了多少个事务。
- `lock_wait_accumulate_weights()`: 计算每个等待事务的权重, 其策略是累加等待事务阻塞的事务权重, 例如事务 t1 阻塞了事务 t2, t3, t5, 则 t1 事务的权重为:t1_weight = t1_weight + t2_weight + t3_weight + t5_weight。
- `lock_wait_publish_new_weights():` 更新等待事务权重。



## **构造wait-for-graph **

T1 → T2 → T3
         ↑            ↓
         T5 ← T4

infos = [T1, T2, T3, T4, T5]
outgoing = [1, 2, 3, 4, 1]  // T1→T2, T2→T3, T3→T4, T4→T5, T5→T2
                              // 存在环: T2→T3→T4→T5→T2



## DFS环检测算法

```c++
static void lock_wait_find_and_handle_deadlocks(
    ut::vector<waiting_trx_info_t> &infos,
    ut::vector<int> &outgoing,
    ut::vector<trx_schedule_weight_t> &new_weights) {

  const uint n = infos.size();
  ut::vector<uint> colors(n, 0);  // 0=未访问, current_color=正在访问
  ut::vector<uint> cycle_ids;
  uint current_color = 0;

  // 对每个未访问的节点进行DFS
  for (uint start = 0; start < n; ++start) {
    if (colors[start] != 0) continue;  // 已处理

    ++current_color;

    // 沿着等待链遍历
    for (int id = start; 0 <= id; id = outgoing[id]) {

      if (colors[id] == 0) {
        colors[id] = current_color;  // 首次访问，标记颜色
        continue;
      }

      // 再次遇到相同颜色 => 发现环
      if (colors[id] == current_color) {
        lock_wait_extract_cycle_ids(cycle_ids, id, outgoing);

        // 验证环的真实性
        if (lock_wait_check_candidate_cycle(cycle_ids, infos, new_weights)) {
          MONITOR_INC(MONITOR_DEADLOCK);
          // 处理死锁
        } else {
          MONITOR_INC(MONITOR_DEADLOCK_FALSE_POSITIVES);
        }
      }
      break;  // 遇到已访问的节点，停止
    }
  }
}

```



## 死锁环存在，选择受害者

```c++
static trx_t *lock_wait_choose_victim(
    const ut::vector<uint> &cycle_ids,
    const ut::vector<waiting_trx_info_t> &infos,
    ut::vector<trx_schedule_weight_t> &new_weights) {

  // 1. 按 reservation_no 排序（最晚加入的排前面）
  auto sorted_ids = lock_wait_order_for_choosing_victim(cycle_ids, infos);

  trx_t *chosen_victim = infos[sorted_ids[0]].trx;

  for (size_t i = 1; i < sorted_ids.size(); ++i) {
    trx_t *trx = infos[sorted_ids[i]].trx;

    // 2. 高优先级事务仲裁
    if (trx_is_high_priority(chosen_victim) || trx_is_high_priority(trx)) {
      auto victim = trx_arbitrate(trx, chosen_victim);
      if (victim != nullptr) {
        if (victim == trx) {
          chosen_victim = trx;
        }
        continue;
      }
    }

    // 3. 比较权重，选择最小的
    if (trx_weight_ge(chosen_victim, trx)) {
      chosen_victim = trx;
    }
  }

  return chosen_victim;
}

```

策略：

- 优先选择最近加入的 
- 选择事务优先级低的，比如后台事务
- 选择权重低的(undo越小，锁越少)。undo_no + t->lock.trx_locks的值越小；代表越容易回滚



## 死锁处理

核心函数 `lock_cancel_waiting_and_release()`: 

- 移除受害者等待锁
- 授予其他等待锁（打破死锁环）
- 唤醒受害者线程回滚 （error_state = DB_DEADLOCK）



后续在`row_mysql_handle_errors()`中处理`DB_DEADLOCK`场景，调用`trx_rollback_to_savepoint()`回滚。





# 四. 锁释放

提交或者回滚的阶段才去释放全部持有的Lock，核心函数在`lock_trx_release_locks()`中，会遍历trx_list上所有lock，依次释放。并将其从**trx_locks**以及全局的**rec_hash**上移除。






# 五. 隐式锁

当事务需要加锁的时，如果这个锁不可能发生冲突，InnoDB会跳过加锁环节，这种机制称为隐式锁。隐式锁是InnoDB实现的一种延迟加锁机制，主要场景是insert 场景。

## Insert 加锁流程

情况一：如果记录之间有Gap_LOCK。为了避免幻读，则不能插入数据。

情况二：如果Insert的记录与已有记录存在唯一键冲突，此时不能插入。

除此以外都不需要加锁。



当后续有请求访问这条记录并尝试加锁的时候，在**lock_rec_lock**加锁之前，需要先判断当前记录上有没有这种隐式加锁的存在。

如果有，则需要创建显式lock。



## 隐式锁转换

场景1：主键索引，判断是否活跃，如果活跃说么没提交。则需要给其加上显式锁

场景2：二级索引；需要回表查询判断是否式活跃事务。

```c++
|	|	|	|-->2.3 can_older_trx_be_still_active()//如果 max_trx_id 小于当前最小活跃事务 ID，说明所有修改都已提交
|	|	|	|-->2.4 row_vers_impl_x_locked() //回表查询
|	|	|	|	|-->2.4.1 clust_rec=row_get_clust_rec()//回表查询主键记录
```

# 六. 锁分裂、继承

锁分裂和合并，只是针对innodb行锁而言的，而且一般只作用于GAP类型的锁。



## 锁继承

`lock_rec_inherit_to_gap()`:让一个记录（heir）继承另一个记录（donor）的锁，但将其转换为 **GAP 锁**。

```C++
static void lock_rec_inherit_to_gap(
    const buf_block_t *heir_block, /*!< in: block containing the
                                   record which inherits */
    const buf_block_t *block,      /*!< in: block containing the
                                   record from which inherited;
                                   does NOT reset the locks on
                                   this record */
    ulint heir_heap_no,            /*!< in: heap_no of the
                                   inheriting record */
    ulint heap_no)                 /*!< in: heap_no of the
                                   donating record */
{
  lock_t *lock;

  //遍历捐赠记录上的所有锁，对每个锁进行判断：
  for (lock = lock_rec_get_first(lock_sys->rec_hash, block, heap_no);
       lock != nullptr; lock = lock_rec_get_next(heap_no, lock)) {
    /* Skip inheriting lock if set */
    if (lock->trx->skip_lock_inheritance) {
      continue;
    }
	
     /**1. 非 INSERT INTENTION 锁
        2. 非 DD 表和 SDI 表 */
    if (!lock_rec_get_insert_intention(lock) &&
        !lock->index->table->skip_gap_locks() &&
        (!lock->trx->skip_gap_locks() || lock->trx->lock.inherit_all.load())) {
      lock_rec_add_to_queue(LOCK_REC | LOCK_GAP | lock_get_mode(lock),
                            heir_block, heir_heap_no, lock->index, lock->trx);
    }
  }
}
```



**场景 1：记录删除**

- 删除记录时，让**下一个记录**继承被删除记录的锁
- 保护被删除记录原本保护的 gap

```C++
|-->lock_update_delete()
|	|-->lock_rec_inherit_to_gap()
```



**场景2： 页分裂**

- 左页的 supremum 继承右页第一个记录的锁
- 保护分裂点的 gap

```c++
|-->lock_update_split_right()
|	|-->lock_rec_inherit_to_gap()
```
