# 1. 项目背景

Neon是一个开源的 Serverless PostgreSQL 数据库平台，其核心创新是存储与计算分离架构，通过将数据分布在集群节点上重新实现了 PostgreSQL 的存储层。

计算节点：与传统 PostgreSQL 不同，Neon 的计算节点是无状态的（Stateless）。它不持有任何持久化数据，其本地磁盘仅用于临时缓存（LFC）和临时文件。当计算节点启动时，

​    它不需要进行漫长的检查点恢复，而是通过网络连接到存储层，直接从最新的日志位置开始服务。

﻿

Safekeepers：负责接收来自计算节点的 WAL 日志流，并通过 Paxos 算法在多个节点间达成共识，确保日志的持久性和一致性。

​    Safekeeper 可以被视为一个高可用的、分布式的预写日志缓冲区。

﻿

Pageserver：负责长期存储和数据服务。Pageserver 从 Safekeeper 拉取已提交的 WAL 日志，并将其处理为易于查询的格式。当计算节点需要读取数据页时，

 Pageserver 会根据请求的日志序列号（LSN）动态重构出该页面的版本。

﻿

对象存储（S3）：作为最终的冷存储层，Pageserver 会将处理后的数据分层上传至云对象存储（如 AWS S3），以实现近乎无限的存储容量和极低的长期存储成本

# 3. 计算节点核心改造

## 3.1 Storage Manager (SMGR) 扩展

在传统 Postgres 中，存储是通过`smgr`（Storage Manager）接口与本地文件系统（POSIX）交互的。

- 核心改动：Neon 引入了一个自定义的存储扩展，挂钩（Hook）了`smgr`接口。
- 应用场景：当 Postgres 需要读取或写入数据页（Page）时，Neon 不再调用`read()`或`write()`本地磁盘，而是将请求封装成 RPC 调用。这意味着对于 Postgres 核心而言，磁盘不再是挂载在`/var/lib/postgresql/data`下的文件，而是一个远端的可编程服务（Pageserver）。

﻿

## 3.2 写路径改动：WAL 拦截与 Safekeeper 机制

在原生 Postgres 中，WAL（预写日志）是确保 ACID 的关键，由`XLogInsert`写入本地磁盘。

- 核心改动：Neon 拦截了 WAL 的落盘过程，将其异步流式传输给Safekeeper集群。
- 应用场景：Neon 并没有修改 WAL 的逻辑格式（保持了 100% 兼容），但它改变了持久化的含义。只有当 WAL 被 Safekeeper 集群（基于 Paxos 协议）确认接收后，计算节点才认为事务提交成功。这让计算节点变得“无状态”，因为它不需要在本地保留任何事务记录。

﻿

## 3.3 读路径改动：GetPage@LSN 范式

这是 Neon 最具创新性的改动。

- 核心改动：当 Postgres 发生 Buffer Miss（缓存未命中）需要从磁盘读页时，它发出的不再是“给我文件 X 的第 Y 块”，而是“给我文件 X 在 LSN（日志序列号）为 Z 时的第 Y 块数据”。
- 应用场景：通过在读请求中携带 LSN，Neon 实现了存储层的多版本并发控制（MVCC）。这使得计算节点可以瞬间完成“快照克隆”或“分支创建”，因为存储层可以根据指定的 LSN 现场重放（Redo）日志，拼凑出任何历史时刻的数据页。

﻿

## 3.4 引入本地文件缓存（Local File Cache, LFC）

由于存储在远端，网络延迟（通常从微秒级跳到毫秒级）是最大的性能杀手。

- 核心改动：Neon 在 Postgres 的`Shared Buffers`之下、远端存储之上，增加了一个基于本地 NVMe 的LFC 层。
- 读取命中：当 Postgres 请求一个页面时，首先检查 Shared Buffers；如果未命中，检查 LFC；如果 LFC 未命中，才向 Pageserver 发起网络请求 2。
- 缓存填充：从 Pageserver 拉取到的页面不仅会被放入 Shared Buffers，也会被写入 LFC。
- 智能驱逐：LFC 的驱逐策略独立于 Shared Buffers。由于 LFC 容量通常远大于内存（例如 100GB+），它可以缓存整个数据库的“工作集”（Working Set）。
- 应用场景：这是一个可动态伸缩的缓存层。它解决了存算分离架构下的延迟抖动问题。由于 LFC 的存在，热数据依然能在本地命中，而冷数据才去远端抓取。这对于支持“缩容至零（Scale-to-Zero）”后的快速冷启动至关重要。

﻿

## 3.5 内核级的预取优化（Prefetching）

原生 Postgres 依赖操作系统的预读（Read-ahead）机制来优化顺序扫描。

- 核心改动：Neon 修改了 Postgres 内核中执行计划（如 Sequential Scan, Index Scan）的底层代码，加入了显式的异步预取（Async Prefetching）。
- 应用场景：在云原生存储环境中，操作系统预读失效了。Neon 必须让 Postgres 提前预知接下来的数据页需求，并通过管道化（Pipelining）发起并发网络请求，以抵消网络往返时间（RTT）对吞吐量的影响。

﻿

# 4. Safekeeper：基于 Paxos 的分布式日志共识

Safekeeper 是 Neon 存储架构中的“写入前哨”，它直接替代了传统架构中的本地磁盘 WAL 写入。其核心职责是低延迟地持久化 WAL，并防止脑裂。

在分布式数据库领域，Raft 往往是共识算法的首选。然而，Neon 选择了自定义实现的 Multi-Paxos。这样可以实现多写（多leader）场景

Neon 的 Paxos 实现将共识协议的角色进行了明确拆分：

- 提议者（Proposer）：PostgreSQL 计算节点。它负责产生 WAL 记录并提议写入。
- 接受者（Acceptor）：Safekeeper 节点。它们负责接收提议，并持久化日志。通常配置为 3 个节点组成的集群。
- 学习者（Learner）：Pageserver 和 Read Replicas。它们从 Safekeepers 那里异步获取已达成共识的 WAL 数据 。

## 日志流程

1. 连接建立：计算节点启动，连接到一组 Safekeepers，发起握手并获取最新的 LSN 和 Term（任期，解决脑裂问题）。
2. 日志流式传输：PostgreSQL 在生成 WAL 记录时，通过网络流式发送给 Safekeepers。
3. 多数派确认：Safekeeper 收到 WAL 后将其写入本地磁盘（通常是高速 NVMe）。当多数派（例如 3 个中的 2 个）完成写入并返回确认后，计算节点认为该 WAL 记录已提交（Committed），并可以向客户端返回事务成功。

﻿

# 5. Pageserver：基于日志结构的存储引擎

它本质上是一个专为 PostgreSQL 页面版本控制而设计的、支持多租户的 LSM（Log-Structured Merge）树存储引擎。

在 Neon Pageserver 中，数据不再以固定的“文件”形式存在，而是被拆解为一系列不可变的层（Layers）文件。这些层文件存储在磁盘上，并在后台上传至 S3。

- Image Layers（镜像层）：存储特定 LSN 时刻的完整 8KB 页面快照。可以将其理解为该时间点的全量备份切片。
- Delta Layers（增量层）：存储一系列 WAL 记录，这些记录描述了对某些页面在特定 LSN 范围内的修改。

这种设计使得 Neon 能够保留数据的完整历史版本，天然支持时间旅行查询（Time Travel Query）

## 5.1GetPage@LSN 协议：拉取式重建

Pageserver 对外提供的核心 API 是`GetPage@LSN(Key, LSN)`。当计算节点请求某个页面在 LSN的版本时，Pageserver 会执行以下逻辑：

1. 索引查找：在内存中中查找覆盖该 Key（页面地址）且 LSN 满足要求的。
2. 路径构建：系统会找到一个最近的“基准”——通常是一个 Image Layer（即 LSN时刻的完整页面）。
3. 重放（Replay）：从基准 Image Layer 开始，Pageserver 会按顺序应用随后所有的 Delta Layer 中的 WAL 记录，直到达到目标 LSN。这个过程是在内存中动态完成的，使用的是一个嵌入式的、精简版的 PostgreSQL WAL Redo 进程 。
4. 返回结果：重构完成的 8KB 页面被返回给计算节点。

## 5.2 存储分层与压缩（Compaction）

为了防止 Delta Layers 无限堆积导致读取性能下降（读放大），Pageserver 必须定期执行 Compaction（压缩）操作。（Neon 的 Compaction 策略受到了 RocksDB 等 LSM 系统的启发）

﻿

## 5.3 分支（Branching）与写时复制（CoW）

Neon 的分支功能是其存储架构的杀手级应用。它允许用户像使用 Git 管理代码一样管理数据库。

### 实现原理

在传统数据库中，克隆一个 1TB 的数据库意味着复制 1TB 的数据块，耗时且昂贵。但在 Neon 中，分支仅仅是一个元数据操作。

创建一个分支本质上是在 Layer Map 中创建了一条新的时间线（Timeline）。这条新时间线包含一个指向父时间线特定 LSN 的指针：Branch B = (Parent: A, Start_LSN: 1000)。

- 读取：当读取分支 B 时，Pageserver 会首先在 B 的时间线中查找 Delta Layer。如果找不到，则回溯到父时间线 A 中查找 LSN < 1000 的数据。
- 写入（Copy-on-Write）：当在分支 B 上进行写入时，新的 WAL 记录只属于分支 B 的时间线。父分支 A 不受任何影响。

这种机制使得创建分支是瞬间完成的（O(1) 复杂度），且不占用额外的存储空间，直到新分支产生差异数据。这意味着用户只需为每个分支产生的差异数据付费，而共享的基础数据只计费一次。

﻿

# 6.Serverless 机制：Scale-to-Zero

### 缩容至零（Scale-to-Zero）的逻辑

当一个项目在一定时间（默认 5 分钟）内没有任何活动连接和查询时，控制平面会触发缩容操作：

1. 监测：监控系统检测到计算节点空闲。
2. 挂起：计算节点进程被终止，Kubernetes Pod 被销毁。由于没有本地持久化状态，这一过程非常快且安全。
3. 状态保存：此时，只有数据在 Pageserver/S3 中持久化保存，计算资源消耗归零 。

﻿

# 7.Neon vs. Amazon Aurora

虽然 Neon 和 Aurora 都采用了“日志即数据库”的理念，但两者在设计细节上有本质区别：

| 特性         | Amazon Aurora                                                | Postgres Neon                                                |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 存储模型     | Push（推送）模型：计算节点将日志推送到存储节点，存储节点在后台不断合并日志生成页面。 | Pull（拉取）模型：计算节点需要页面时，向 Pageserver 请求，Pageserver 按需重构页面。 |
| 共识协议     | Quorum (6 副本写 4)。                                        | Multi-Paxos (3 副本写 2)。                                   |
| 计算节点状态 | 有状态（Warm Buffer Pool）。重启后缓存依然有效。             | 无状态（Stateless）。依赖 LFC 和快速重构来预热。             |
| Serverless   | 主要是自动扩缩容                                             | Scale-to-Zero                                                |
| 分支能力     | 克隆（Clone）基于存储卷快照，虽然也是 CoW，但通常较重。      | 基于时间线的轻量级分支，支持任意时间点，更接近 Git 体验。    |
| 开源协议     | 闭源                                                         | 开源（Apache 2.0）                                           |
